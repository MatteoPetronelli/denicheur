# Professional Git Commit Workflow

Standards and conventions for crafting high-quality, professional Git commits with clean developer attribution.

## When to Use
- The user requests to commit code, create a git commit, save changes, or write a commit message.
- Structuring conventional commits with architectural clarity and optional issue references.
- Preparing production-ready commits across solo and team repositories.

---

## 1. Branch Safety & Workflow Adaptability

Before committing, verify the active branch:

```bash
git branch --show-current
```

### Solo vs. Team Mode
- **Personal / Solo Projects**: Direct commits to `main` or `master` are fully permitted when working on personal projects, independent repositories, or local feature work where remote branch protection is not active.
- **Team / Protected Repositories**: If the repository is configured with upstream branch protections, requires pull requests, or the user explicitly specifies `--branch <name>`, create and checkout a feature branch before committing.
- Do not halt or prompt for unnecessary branch creation on solo repositories.

## 2. Commit Format & Schema

Every commit must follow the Conventional Commits specification:

```
<type>(<scope>): <Subject>

<Body>

<Footer>
```

- **Header**: Required. Max 70 characters.
- **Scope**: Optional but recommended when changes focus on a specific subsystem (e.g. `ast`, `client`, `watcher`, `output`).
- **Body**: Required for non-trivial changes. Max 100 characters per line.
- **Footer**: Optional. For issue tracking or breaking change announcements.

### Commit Types

| Type | Purpose |
|------|---------|
| `feat` | New feature or capability |
| `fix` | Bug fix or defect resolution |
| `ref` | Refactoring without altering external behavior |
| `perf` | Performance or memory optimization |
| `docs` | Documentation additions or revisions |
| `test` | Adding or updating tests |
| `build` | Build system, toolchain, or dependencies |
| `ci` | CI/CD configuration and pipeline scripts |
| `chore` | Maintenance tasks and codebase hygiene |
| `style` | Formatting, whitespace, or lint cleanups |
| `meta` | Repository configuration or manifests |
| `license` | License additions or updates |

### Subject Line Rules
- Use imperative, present tense: `"Add feature"`, not `"Added feature"` or `"Adds feature"`.
- Capitalize the first letter.
- Do not place a period (`.`) at the end.
- Maximum length: 70 characters.

### Body Guidelines
- Focus on **what** changed and **why**, rather than mechanical line-by-line implementation details.
- Use imperative mood and present tense.
- State the architectural rationale and motivation for the change.
- Hard wrap all body lines at or below 100 characters.

---

## 3. Author Identity & Clean History Policy

Commits must be authored solely by the developer registered in the local Git configuration (`git config user.name` and `git config user.email`).

- **Strict Ban on AI Trailers**: Never inject artificial co-authorship trailers, such as `Co-Authored-By: ...`, `Generated by AI`, `Assisted-by`, or third-party vendor tags.
- **Clean Developer Attribution**: Keep git history clean, professional, and personal to the repository owner and human contributors.

---

## 4. Footers & Issue References

Reference issues and breaking changes in the footer when applicable:

```
Fixes #1234
Refs #5678
BREAKING CHANGE: Describe breaking API or contract change
```

- `Fixes`: Automatically resolves the linked issue upon merge.
- `Refs`: Links discussion or tracking tickets without resolving.

## 5. Examples

### Standard Feature
```
feat(watcher): Add async stream cancellation and decoupled watcher loop

Decouple filesystem watch events from the Ollama inference pipeline to
prevent terminal lockups during rapid file edits. Introduce cooperative
cancellation tokens to abort obsolete generation streams immediately upon
detecting new modifications. Enforce a 15-second per-chunk read timeout
on the SSE stream to guard against GPU memory deadlocks.
```

### Bug Fix with Issue Reference
```
fix(api): Handle null response in user endpoint

The user API could return null for deleted accounts, causing an unhandled
panic in the dashboard route. Add defensive guard clause before accessing
user profile properties.

Fixes #5678
```

### Refactor
```
ref(parser): Extract common validation logic to shared module

Move duplicate syntax validation routines from AST modules into a unified
validator helper. No behavior change.
```

### Breaking Change
```
feat(api)!: Remove deprecated v1 endpoints

Remove legacy v1 query endpoints. Consumers must migrate to the v2 streaming
pipeline API.

BREAKING CHANGE: v1 query endpoints are no longer supported
Fixes #9999
```

---

## 6. Principles
- Each commit must represent a single, cohesive, working state.
- Commits must pass compilation and test suites before execution.
- Maintain clean, professional, human-owned Git logs.
